User's example: right-clicking the desktop does not use the border colour set in Windows settings. ## What is done
1. **Root cause found and proven from the mod's own debug log.** Windows paints `MENU_POPUPBACKGROUND` (part 9) *after* `MENU_POPUPBORDERS` (part 10) on some menus: `tf-winver.exe-46284.log` ends its menu pass with `[border] clip=0,0,165,50 color=FF89B4FA useDefault=0 useNone=0` followed by another `[dtb] part=9`. Both parts shared one whole-clipRect `BLACKNESS` fill, so the accent frame the border branch had just drawn was erased again. Measured on that 165x50 menu: 0 of 430 outline pixels matched the accent. The order is not stable, which is why the ring was present on 13/10 and gone on 17/10 at 6:58 PM with the same 0.6.33 DLL — so this was never a version regression.
2. **Fix written** in `Windhawk\translucency-flyouts\src\30-engine.inc` (version 0.6.34):
   - the `MENU_POPUPBORDERS` branch records the rect it paints: `state->outlineRect = clipRect;` (authoritative for the menu being painted; a buffered paint can resolve a different menu window, whose size would reserve the wrong ring);
   - `HandleMenuDrawThemeBackground` still stops the black fill one pixel inside `outlineRect`, and now re-frames the full window rect after every band, with the clip dropped for the frame only (`SelectClipRgn(hdc, nullptr)` under `DcStateGuard`), so the outline sits on top of whichever band painted last. Framing the band's own clip is what used to leave a tick at each band's right edge, which the old comment warned about.
   - The `TF_DEBUG_LOG` instrumentation from gen 2 is kept, all guarded by `#ifdef TF_DEBUG_LOG` (`[dtb]` part/state/dcWnd/menu, `[dwm] border`, `[border]` clip+colour+useDefault/useNone). Release builds compile it out.
3. **Built**: x64 + x86, release (no `-DebugLog`), via `scripts\2026-09-28-translucent-flyouts-build.ps1` with `-EngineLibRoot 'C:\Program Files\Windhawk\Engine\2.0.0_1'` (the 1.7.3_2 default in that script is stale). sha256: `4C5D60D5E8D46C986DF9202FE001F5A0FDD5AB3155F5173DD2167EE664C80026` (64), `173CEF939CE093041F717DCD6DF9DAB2365319436295B25ED0558894DC93DE0E` (32).
