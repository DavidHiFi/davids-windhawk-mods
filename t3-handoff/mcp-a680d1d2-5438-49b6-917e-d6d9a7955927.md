## Key code facts (answers forming)

- `ApplyWindowStack` (line 614): sets `WCA_FORCE_ACTIVEWINDOW_APPEARANCE` (=15, line 138)
  TRUE when `nativeTitleBar && titleBarAcrylic && blur` (all true live) — forces the
  window to render as active ALWAYS; SBT=3 + ExtendFrame(-1); DWMWA_CAPTION_COLOR=NONE
  in acrylic mode; **DWMWA_TEXT_COLOR set ONLY if `s.text` non-empty — live text is
  EMPTY, so it is never pinned** (DWM uses its default, which auto-dims on real
  inactivity); DWMWA_BORDER_COLOR=NativeBorderColor(hwnd) which DOES read activation
  (GetForegroundWindow()==hwnd → AccentColorMenu else AccentColorInactive).
- `MainWindowProc` subclass (line 932): line 991-993 —
  `if (message == WM_NCACTIVATE && s.nativeTitleBar && s.titleBarAcrylic && s.blur)
  return DefSubclassProc(hwnd, message, TRUE, lparam);` — swallows real activation and
  always tells the default proc "active" (exact mirror of the FreeDictate swallow).
- `DwmSetWindowAttribute_hook` (1082): corrects CAPTION/TEXT/BORDER puts in-call;
  for TEXT_COLOR with empty setting it passes foreign puts through ("let the app's
  color stand") — if the shell pushes a dim text color it sticks verbatim (per
  FreeDictate finding, a custom-set DWMWA text color is used verbatim; DWM only
  auto-dims its default). Backdrop re-assert on focus changes already exists (1090-1100).
- `PaintCaption` (810, called from WM_PAINT at 1005): paints strip tint (buffered paint,
  alpha = backgroundOpacity 75) + title text via `DrawThemeTextEx(WP_CAPTION, CS_ACTIVE)`
  — ALWAYS the ACTIVE theme part, crText = white (255,255,255) when text setting empty;
  paints icon; does NOT paint buttons.
- `IntegratedCaption(s) = nativeTitleBar && titleBarAcrylic`; WM_NCCALCSIZE folds the
  client to the full window (client->top = frameRect.top + inset), WebView child
  (`WRY_WEBVIEW`) is cropped below the caption height (`CropCaptionChild`); DWM still
  draws the caption BUTTONS over the strip (DwmDefWindowProc hit-testing, line 940).
- Worker thread (1586): every ~1 s re-reads settings and re-asserts
  (`ApplyToOurWindows` → `ApplyEnumProc` → `ApplyWindowStack`; re-apply runs every
  cycle in acrylic mode because the DwmGetWindowAttribute read fails E_INVALIDARG).
- SetWindowCompositionAttribute import is extern "C" from user32 — sound; attribute
  value 15 matches the 2.0.8 note ("composition attribute 15").

## Central contradiction (must resolve before finalizing the plan)

Code analysis predicts the caption is ALWAYS BRIGHT (forced-active appearance +
WM_NCACTIVATE forced TRUE + text always painted CS_ACTIVE/white). The owner reports
ALWAYS GREY/DIMMED even focused. Candidate explanations to discriminate:
(a) the forced-active machinery no longer affects DWM's caption text/glyph rendering
on this build; (b) the owner's "grey/dimmed" is the constant SBT-acrylic strip +
pinned text reading as dim vs native (i.e. the caption never transitions at all);
(c) a foreign TEXT_COLOR put is passed through by the hook (text setting empty) and
sticks verbatim. The fix direction is to let the caption follow REAL activation
(conditionalize/remove the WM_NCACTIVATE TRUE swallow at 991-993 and the
WCA_FORCE_ACTIVEWINDOW_APPEARANCE at 615-617, e.g. behind a setting), while keeping
the existing in-call backdrop correction so the acrylic strip doesn't flash — but the
2.0.8 note warns the forced-active look was what avoided the flat inactive (84,84,84)
fill, so the plan must weigh native dim behavior vs that regression and include a
setting to flip back.
